Подсистема реализует полный цикл работы: от скачивания сырых списков адресов до BGP-анонсирования готовых маршрутов. Взаимодействие компонентов строится в виде конвейера обработки данных (Pipeline).

Архитектура и алгоритм работы конвейера
Логика работы подсистемы разделена на 5 последовательных этапов:

1. Инициализация конвейера (Планировщик)
Запуск процесса обновления происходит циклически, полностью в автоматическом режиме.

Триггер: Системный планировщик cron.
Расписание: Каждые 20 минут.
Действие: От имени суперпользователя (root) запускается главный скрипт-оркестратор /xxx/force-refresh.sh.
2. Сбор и агрегация сырых данных (get-prefixes.sh)
Оркестратор делегирует сбор данных скрипту /xxxx/get-prefixes.sh (с понижением привилегий до пользователя xxxx). На этом этапе формируются первичные списки «на включение» и «на исключение».

Внешние источники (Online Feeds): Загрузка актуальных списков IP-адресов и подсетей по URL-адресам (репозитории GitHub, сервисы antifilter.network, официальные диапазоны Google, Telegram, RIPE). Происходит базовая фильтрация скачанных данных с помощью регулярных выражений для выделения валидных IPv4-адресов.
Локальные дополнения (Inclusions):
Обработка пользовательских списков. Скрипт читает файл xxxx, выполняет DNS-запросы (через dig) для каждого домена и добавляет полученные IP-адреса в виде хостовых маршрутов (/32).
Читает файл xxxx и напрямую добавляет указанные подсети.
Локальные исключения (Exclusions / Direct): Аналогичным образом формируются списки адресов и доменов, трафик к которым должен идти напрямую (файлы xxxx и xxxx).
3. Математическая оптимизация и слияние (cidr-merge.py)
Собранные массивы данных передаются в Python-скрипт cidr-merge.py для оптимизации таблицы маршрутизации.

Ограничение гранулярности: Скрипт принудительно ограничивает максимальную длину префикса значением /28. Меньшие подсети (/29, /32) расширяются, что позволяет радикально сократить итоговое количество строк в таблице маршрутизации.
Объединение: Смежные и перекрывающиеся диапазоны IP-адресов объединяются в более крупные CIDR-блоки с помощью библиотеки netaddr.
Применение исключений: Скрипт вычитает массив локальных исключений из общего проксируемого пула. Если исключенный IP-адрес находится внутри крупной проксируемой подсети, скрипт математически корректно дробит эту подсеть, гарантируя, что исключенный адрес не попадет в итоговый список.
4. Подготовка конфигурации для маршрутизатора
Оптимизированный список IP-сетей форматируется bash-скриптами в синтаксис статических маршрутов демона BIRD2.

Каждой подсети присваивается тип blackhole (формат: route <подсеть> blackhole;).
Итоговый файл сохраняется по пути xxxx.
Оркестратор force-refresh.sh отправляет команду configure в консоль birdc, заставляя демон маршрутизации применить новый файл без перезапуска службы.
5. Изоляция и BGP-анонсирование (BIRD2)
Служба BIRD2 выступает в роли BGP-инжектора (Route Injector).

Загрузка списка: BIRD2 считывает сформированный конфигурационный файл (protocol static target_subnets), но не импортирует эти маршруты в таблицу маршрутизации операционной системы самого сервера IGW (import none; export none; в protocol kernel) — они предназначены исключительно для передачи на внешний маршрутизатор.
BGP-сессия: IGW устанавливает BGP-соединение с главным маршрутизатором предприятия.
Экспорт маршрутов: Входной сервер транслирует внешнему маршрутизатору только маршруты из сформированного в предыдущих шагах списка (export where proto = "target_subnets"); импорт любых внешних маршрутов отключён (import none).
