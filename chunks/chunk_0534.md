Да. Я посмотрел RFC по GRE-in-UDP и 3GPP TS 29.281 по GTP-U. Если идея такая: взять GRE, завернуть его в UDP и сделать поток максимально похожим на GTP-U в LTE/4G, включая поведение при фрагментации, то на уровне «UDP-трафик между двумя узлами» сходство получить можно, но по всем фронтам GRE-in-UDP не становится GTP-U. Нормальный GTP-aware DPI отличит их довольно быстро.
Ключевой момент: стандартный стек GRE-in-UDP выглядит примерно как outer IP → UDP → GRE → inner IP, тогда как LTE user-plane — outer IP → UDP → GTPv1-U → T-PDU. RFC 8086 прямо определяет GRE поверх UDP и использует стандартный destination port 4754 (4755 при GRE+DTLS); GTPv1-U использует UDP/2152. 
Но порт — это самая поверхностная часть. У настоящего GTP-U есть TEID, который идентифицирует конкретный туннель на принимающей стороне. TEID назначается принимающим GTP endpoint и передаётся второй стороне через control-plane механизмы вроде GTP-C/S1-AP. То есть DPI может смотреть не только на UDP/2152, но и на согласованность GTP header, message type, TEID и состояния туннеля. 
Для обычного user-plane трафика GTP-U используется сообщение G-PDU (message type 255), после GTP-U header идёт исходный T-PDU. Кроме того, у протокола есть Echo, Error Indication, End Marker, Supported Extension Headers и расширения GTP-U. Поэтому простой GRE/UDP с похожими размерами пакетов не воспроизводит протокольное состояние GTP. 
Самая интересная часть твоего вопроса — фрагментация. Здесь GRE-in-UDP и GTP-U стандартизированы несколько по-разному.
RFC 8086 рекомендует для GRE-in-UDP делать fragmentation до encapsulation: входной пакет режется на части с учётом PMTU, а затем каждый фрагмент отдельно получает GRE+UDP encapsulation. Причём RFC рекомендует использовать один и тот же UDP source port для частей одного пакета, чтобы ECMP не раскидал их по разным путям. 
У GTP-U 3GPP явно рассматривает outer fragmentation уже получившегося IP/UDP/GTP/T-PDU. Если после добавления GTP+UDP+outer-IP пакет превышает MTU, sending endpoint должен фрагментировать внешний IP datagram. На стороне egress GTP endpoint эти outer IP fragments сначала полностью reassemble, и только потом результат передаётся UDP/GTP-U и из него извлекается inner packet. 
То есть концептуально:
GRE-in-UDP, рекомендуемый RFC 8086:

inner packet
    ↓ fragmentation
frag A     frag B
  ↓           ↓
GRE/UDP     GRE/UDP
  ↓           ↓
network
А разрешённый механизм GTP-U:
inner packet
    ↓
GTP-U
    ↓
UDP
    ↓
outer IP
    ↓ outer fragmentation
IP frag A  IP frag B
       ↓
     network
       ↓
outer IP reassembly
       ↓
 UDP → GTP-U → inner packet
Именно поэтому, если под «обратной фрагментацией» ты имеешь в виду получение фрагментов на другом конце и их обратную сборку перед decapsulation, то да — для GTP-U это прямо предусмотрено 3GPP. Получатель должен собрать outer-IP datagram и только после этого передать его UDP/GTP слоям. Буфер reassembly должен вмещать как минимум inner MTU плюс outer IP/UDP/GTP headers. 
При этом обратное направление LTE — не «обращение» исходной фрагментации. UL и DL фактически являются самостоятельными направлениями передачи через соответствующий tunnel context; размеры пакетов, PMTU и факт фрагментации могут быть асимметричны.
Ещё важное различие — entropy/UDP source port. В GRE-in-UDP source UDP port специально является entropy field для ECMP. В современном GTP-U 3GPP тоже допускает динамический UDP source port для балансировки transport network, поэтому по одной только динамике source-port эти два случая действительно могут выглядеть похоже. Но GTP-aware анализ затем видит заголовок GTP и TEID.
